# Contributing

This guide explains how to set up a local development environment, run the
test suite, and keep the code quality gates green. The project is an
educational Sudoku PWA: a React frontend plus a Go solver that is also
compiled to WebAssembly.

## Prerequisites

- **Go** 1.26 or newer (solver, dev API server, WASM build).
- **TinyGo** 0.40.1 (required only to rebuild the WASM solver; the
  committed build in `frontend/public/sudoku.wasm` is gitignored and is
  regenerated by `make wasm`).
- **Node.js** 24 or newer (frontend dev server, tests, lint).
- **Docker** (used to run E2E and unit tests with CI parity, and for the
  `make dev` / `make prod` dev servers).

## Getting the Code

```bash
git clone git@github.com:ThoDHa/sudoku.git
cd sudoku
```

## Running the Frontend Locally

The development server is frontend-only. The Go solver runs in the browser
as WASM; the Go HTTP server in `api/cmd/server` is optional (see
[ARCHITECTURE.md](ARCHITECTURE.md)).

### With Docker (recommended)

```bash
make dev
# App available at http://localhost
```

`make dev` first rebuilds the WASM solver (so the served solver always
matches current Go source) and then runs the Vite dev server inside Docker.

### Without Docker

```bash
cd frontend
npm install
npm run dev
# App available at http://localhost:5173
```

The WASM solver must already exist at `frontend/public/sudoku.wasm`; run
`make wasm` from the repo root to build it if it is missing.

## Running the Optional Go Dev Server

The Go HTTP server exposes the same solver packages over gin routes. It is
not started by `make dev` and is not needed for normal frontend work.

```bash
cd api
JWT_SECRET="$(openssl rand -hex 32)" make run
# Server listens on :8080 by default
```

`JWT_SECRET` must be set and at least 32 characters long; the config loader
in `api/pkg/config/config.go` refuses to start otherwise. The route
contract is documented in [docs/dev-api-reference.md](docs/dev-api-reference.md).

## Rebuilding the WASM Solver

The WASM module and its `wasm_exec.js` glue are build outputs, not source.
Regenerate them whenever you change Go solver code:

```bash
make wasm          # TinyGo build (default, ~600KB output)
# or, if TinyGo is unavailable:
cd api && make wasm-all-go   # standard Go fallback (larger output)
```

## Running Tests

All test targets produce Allure output under `allure-results/`.

| Target                  | What it runs                                |
| ----------------------- | ------------------------------------------- |
| `make test`             | Go tests + frontend unit + E2E (full suite) |
| `make test-go`          | Go test suite only                          |
| `make test-unit`        | Frontend Vitest unit tests (Docker)         |
| `make test-e2e`         | Playwright E2E tests (Docker Compose)       |
| `make test-integration` | `@integration`-tagged E2E tests only        |
| `make test-frontend`    | Frontend unit + E2E                         |
| `make test-scripts`     | Report-portal script tests (drift guard)    |

### Fast pre-push gates

```bash
make check-fast   # lint + Go + frontend unit (tight dev loop)
make check        # full local gate mirroring CI (adds coverage, duplication, vulncheck)
```

`make check` is the recommended gate before pushing: if it passes locally,
CI passes. E2E is intentionally excluded from both; run `make check-full`
for the slow end-to-end gate.

## Comment Policy

Comments are absent by default. Before writing one, try to make the code express itself: rename
things, extract a helper, simplify the expression. A comment is permitted only when all three
hold: the code cannot carry the intent, the comment explains a non-obvious WHY (not WHAT), and
removing it would leave a future reader genuinely confused.

Never in comments: tracker IDs (BUG-123, INFRA-4), fix chronology ("previously", "before the
fix"), attribution, or restatements of what the adjacent code does. Bug-fixing history belongs
in commit messages; the WHAT belongs in the code. Exemptions: `Stryker disable` directive
justifications (the prose is the directive's data), `istanbul ignore` regions, and the
eslint-required comments in intentionally empty catch blocks.

## Linting and Formatting

| Target                    | Scope                                                                      |
| ------------------------- | -------------------------------------------------------------------------- |
| `make lint`               | Go (`golangci-lint`) and frontend (`eslint`)                               |
| `make lint-go`            | Go only; installs the pinned `golangci-lint` (`v2.12.2`) into `GOPATH/bin` |
| `make lint-frontend`      | Frontend ESLint with the shared warning budget (`--max-warnings 13`)       |
| `make format`             | Prettier + `gofmt` in place                                                |
| `make format-check`       | Prettier + `gofmt` check only (CI-friendly)                                |
| `make typecheck-frontend` | `tsc --noEmit` for production and test configs                             |

The Go linter uses a strict zero-warning configuration (`.golangci.yml`).
The frontend linter, CI, and the pre-commit hook all share the same ESLint
warning budget so a local green run matches CI.

## Pre-Commit Hook

The repository ships a pre-commit hook that enforces the shared lint budget
before a commit lands. It auto-detects which file types are staged:

- frontend `.ts` / `.tsx` files trigger ESLint,
- Go `.go` files trigger `golangci-lint`.

The hook blocks the commit if ESLint warnings exceed the budget or
`golangci-lint` reports any issue. Install it with the project's hook setup
(the hook script lives under `scripts/`).

If you must bypass the hook in a genuine emergency, `git commit --no-verify`
does so, but this should be rare. Fixing the lint issue is always preferred.

## Test Reports

Each deploy publishes a unified report portal at
<https://thodha.github.io/sudoku/reports/> linking the Allure report, the
mutation testing reports (StrykerJS for the frontend, go-mutesting for Go),
and the nightly profiling report. To regenerate an Allure report locally
from the latest `make test` run:

```bash
make report         # dated report under reports/<timestamp>-allure/
make serve-reports  # serve it on http://0.0.0.0:8099
```

## Regenerating Practice Puzzles

Practice puzzles are pre-sorted by required technique. Regenerate them with:

```bash
cd api && go run ./cmd/generate_practice \
  -puzzles ../frontend/puzzles.json \
  -o ../frontend/practice_puzzles.json \
  -max 5
```

## Project Layout

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full module map and runtime

server, `frontend/` holds the React PWA, and `tools/` holds development
utilities.
